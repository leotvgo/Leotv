# 流浪壳 261124 与 Leotv 的 TMDB 加载链路比较

本次按用户提供的两个 APK 反编译，调查 TMDB API、Key、图片域名、请求顺序、缓存、DNS 和并发。调查对象为 Leotv 当前 5.3.1 / 639 的生产源码，以及流浪壳 32/64 位 261124；未修改应用功能、发布版本或构建 APK。

## 结论

**两个壳的默认 API 和内置 Key 完全相同。流浪壳的快速显示主要有明确的实现依据：搜索结果先显示、详情后台补齐、持久缓存、请求合并，以及针对 TMDB 的并发 DNS。** 用户设备上各项贡献多少，仍需带阶段耗时的实际运行记录确认，不能从 APK 静态代码断言每次冷加载都能一秒完成。

我们已定位两个直接影响可见速度的等待点：详情要等豆瓣评论等补充请求结束才统一 render；首页轮播要等前面三项全部完成才首次提交。我们现有的 `MetadataPrefetch` 没有接入当前首页/详情的生产入口。

## 流浪壳怎么让内容先显示

### 1. 搜索结果直接形成首屏资料

`vg3.x → vg3.w` 清理标题后请求 `/search/multi`，无匹配时才按拆分标题补一次搜索。`vg3.p` 直接从搜索结果读取海报、背景图、简介、年份、分类、媒体类型和评分，形成十项轻量数组。

首页任务 `n62.run` 把这个数组写入 `gi3.e`，保存缓存并通知订阅者；额外详情交给 `pw1` 在工作池执行。聚焦/详情任务 `rh3.run` 同样在搜索成功后先调用 `gi3.S` 通知界面，随后才排入补充任务。原 smali 已核对这个先后顺序。

所以很多情况下，用户感知的“TMDB 已加载”只需要一条搜索响应，详细资料随后继续完善。

### 2. 详情请求较轻，并合并已知季的数据

`vg3.h` 的电影详情使用 `append_to_response=images`；电视剧在已知季号时使用 `images,season/<N>`，把当前季合并到作品请求。没有在这一请求里附加我们当前详情使用的演员、推荐、评论、视频、external_ids、keywords、similar 等整套字段。

这不是建议删除我们已有的信息。可以保留全部模块，改变它们获取和显示的时序。

### 3. 下次启动仍能命中元数据缓存

`gi3.<clinit>` 从配置存储恢复 `tmdb_poster_cache`、`tmdb_poster_ids`、`tmdb_scores`、`tmdb_seasons` 和时间记录，采用 `tmdb_poster_fingerprint=v8` 作为格式失效标识。`gi3.i0` 将元数据 map 序列化保存。

`gi3.j` 命中缓存后立即回调界面，缺背景、缺集数、缺 logo 或需要更新时另外调度补充任务。未完结剧集有约一小时的集数复查条件；缺背景图的重试时间记录使用一天的间隔。不能把这些间隔当作所有字段统一过期时间。

`gi3.c/d` 合并同名作品的在途请求和多个回调，减少重复搜索。首页预取启动最多四个调度器，任务用计数限制搜索并发；补充任务另有计数、去重和延迟重试。共用的工作池有 20 个线程，但这不等于同时发起 20 条 TMDB 搜索，也不等于应该原样搬到 Android 6 电视盒子。

### 4. DNS 竞争和连接复用

`vg3` 的 6 秒客户端和 2 秒 logo 客户端由 `y82.c().newBuilder()` 创建，共用连接池、DNS 和其它基础网络配置。连接池为最多 32 条空闲连接、保留 5 分钟。Dispatcher 的配置为总请求 64、单主机 15；实际 TMDB 使用同步 `execute()`，并发还受上面的任务调度限制。

`v82.lookup` 对包含 `tmdb.org` / `themoviedb.org` 的主机并发尝试系统 DNS 和两个 DoH 服务：

- `https://223.5.5.5/dns-query`
- `https://119.29.29.29/dns-query`

最先返回成功列表的任务唤醒等待者，等待窗口为 2 秒，没有结果再调用系统 DNS；如果用户已有指定 DoH，优先使用该配置。它竞争的是解析结果，**不是自动验证哪个 IP 的图片下载最快**。

### 5. 图片测速与手动指定 IP 是额外能力

`rd1.b` 对指定 IP 以真实图片路径发起 HTTPS 请求，连接超时 1.5 秒、读取超时 20 秒，使用 `Range: bytes=0-1048575` 测量首响应和下载速度，拒绝失败响应及 text/JSON。测速窗口可并发使用五个预设图片样本。

`kd1.onClick` 在用户勾选“强制使用”时把主机/IP 放入 `a73` 的进程内字段；`rd1.lookup` / `lh2.lookup` 在图片客户端中读取它。取消勾选恢复自动解析。没有发现这处强制 IP 状态写入持久存储，也没有依据把手动测速功能描述为默认每次启动自动优选 IP。

这部分是流浪壳已有的额外设置能力。我们本次只调查；新增设置入口或迁移功能另按项目规则确定范围。

## 我们已定位的等待与重复工作

| 位置 | 当前实际行为 | 对可见速度的影响 |
| --- | --- | --- |
| `DetailActivity.enrich` | 等 `MobileDetailMetadata.load` 完整返回后才 `page.render(result)` | 已取得的海报/简介无法提前显示 |
| `MobileDetailMetadata.loadTmdb` | 搜索、必要时逐个消歧、全字段详情、当前季、豆瓣评论、必要时合集依次执行 | 附加内容会累积到首屏等待时间 |
| `loadDoubanReviews` | TMDB 成功后仍同步调用豆瓣短评/长评链路 | 豆瓣慢也会被用户感知为“TMDB 很慢” |
| `DoubanReviewMetadata` | 缓存属于客户端实例；详情每次新建客户端 | 非当前详情 session 的反复进入不一定复用评论缓存 |
| `CspHeroMetadata.load` | 三条工作线程，首次回调等待前面三项都完成；最后再整体提交 | 第一项已完成时仍可能被第二/第三项阻挡 |
| `CspHeroMetadata` → 详情 | 轮播匹配结果存于首页视图列表；没有接入共享元数据缓存 | 点击可能再次搜索/请求同一作品 |
| `MetadataPrefetch` | 当前生产源码中没有 `prefetch()` / `load()` 调用点 | 不能按该类注释认定预取已生效 |
| `DetailSessionCache` | 最多约 12 项、进程内、按站点/资源/设置隔离 | 返回当前详情有效；应用重启后重新获取资料 |
| `BackdropHttp` | 每次使用 `HttpURLConnection`、系统解析，读取后 disconnect | 无流浪壳显式的共享 OkHttp/DNS 路径；握手复用损耗需实际测量 |
| `TmdbRoutes` | 自动比较官方域名的有效响应 | 已有域名选择能力，但不解决资料提交时序和跨启动元数据缓存 |

我们已有 `BackdropImages` 图片磁盘缓存，因此准确问题是**元数据缓存及其调用链不充分**，不能笼统说我们没有缓存。

冷加载电视剧的常见链路为：线路详情 → TMDB 搜索 → 全字段作品详情 → 季详情 → 豆瓣作品匹配/短评/长评 → render → 图片读取。部分条件可跳过请求；同名作品消歧、缺演员、合集和评论翻页会增加请求。

首页另有 `loadHero` 轻量详情路径，虽然不等豆瓣评论，但仍须先搜索再请求 `images`，并受首次三项提交条件影响。

## 本机网络取证的边界

对公开电影 550 做了两轮直连请求，每轮五条独立连接并发，开启 API 压缩并保留 TLS 校验：

| 请求 | 解压后 JSON | 两轮总耗时 |
| --- | ---: | --- |
| 搜索 `Fight Club` | 8,644 字节 | 1.37 / 1.60 秒 |
| 详情附加 `images` | 3,175 字节 | 0.91 / 1.21 秒 |
| 我们电影详情的全附加字段形态 | 145,691 字节 | 1.71 / 1.11 秒 |

全字段响应体明显更大，但第二轮并没有比轻量请求更慢；不能用这两轮数据断言附加字段一定增加多少时间。本机 DNS 本次约 5–10ms，也不能用此证明所有用户设备都存在 DNS 慢。

更有把握的是代码中的串行等待和缓存未接入：它们直接决定哪些请求结束后才能显示。网络样本不测量两个 APK 的真实运行耗时，未访问设备数据，也没有复刻流浪壳实际的连接池或缓存命中状态。

## 建议的修复顺序

1. 保留现有完整功能，先提交可靠匹配的海报、背景、简介和评分；季、演员、评论、推荐、合集等在后台补齐。特别把豆瓣评论移出首屏等待。
2. 首页首个可用作品及时提交，避免前面三项互相阻挡；让首页取得的 TMDB ID 和轻量资料被详情复用。
3. 接通统一的在途请求合并与有界元数据缓存，再补跨启动缓存。按 API、Key 指纹、语言、手动匹配及作品身份隔离，维护原同名/季数匹配规则。
4. 保留我们现有域名自动选择，把已验证的 `images.tmdb.org` 纳入图片候选；独立核对 Android 6 根证书覆盖。按原 TLS 校验、取消、超时和代理契约实现连接复用与 DNS 竞争。

直接替换 Key 没有意义，因为已经是同一个。手动 IP 测速 UI 属于额外功能，不是这些速度修复的必要前提。后续若进入代码修复，按现有规则直接推送 GitHub 构建四套固定签名 APK，保留必须门禁，运行效果由用户真机验收。
