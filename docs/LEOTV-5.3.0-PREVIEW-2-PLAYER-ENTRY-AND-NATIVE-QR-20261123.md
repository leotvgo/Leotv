# Leotv 5.3.0-preview.2 / 614：弹幕入口、TV 原生扫码和播放标题

用户确认上一版手机普通分类分页已解决；报告播放控制栏没有手动搜索入口，要求先修复推送以便真机测试 API，同时要求 TV 扫码 UI 与原生属性一致。之后报告手机安装 TV32/64 位包触屏唤醒时顶部标题/属性缺失，要求保留已经修复的黑色进场背景。用户说明 coos-js 地址是标准弹幕服务转发入口，并要求后续 TVBox 订阅输出弹幕参数。按持续授权只改 APK，直接编译测试包，不新增本地回归。

## 播放入口

对照原 `P3.b.onCreate` 和 `M3.b.onCreate`：手机先 `O(Bundle)` 再 `N()`，TV 先 `L()` 再 `K()`。上一版在前者尾部安装弹幕监听，随后被原 initEvent 覆盖；原 XML 还将 `danmu` 控件默认设为 gone。现在播放器会话仍在原初始化阶段建立，按钮安装独立放在 `N/K` 完成后，播放结果和控制栏唤醒时也恢复。

无论是否配置地址，原生底部动作栏显示“弹幕”，短按打开“搜索弹幕 / 本地文件 / 弹幕设置 / 显示开关 / 来源”菜单，长按切换显示。不是额外叠加一个悬浮搜索按钮。保留原控制按钮字体、背景和位置，TV 恢复后运行原 `H0` 重新连接相邻遥控焦点。

## TV 原生扫码 UI

扫码入口从普通 TextView、像素 padding 和 selector_item 改为克隆原 `dialog_ua` 的 positive 按钮，沿用原字体、selector_text、颜色状态和焦点反馈。TMDB Key/域名扫码按钮同排，按原 dp 间距排列；单字段入口也使用同一按钮。所有输入使用原弹窗主题 Context 的 CustomEditText。

二维码弹窗直接使用原 `dialog_ua` 完整布局和内部 positive/negative 控件，不再隐藏原按钮后套入另一层标题/Material footer。说明文字读取原 info 控件并使用输入框的主题提示色；保留原二维码、输入、间距和左右关系。确认按钮回填外层字段，外层保存验证仍存在。宽度沿用原 55% 窗口比例，并在窄屏 TV 模拟环境中约束到可用窗口。

原本机二维码生成、手机网页、文本接收和订阅广播隔离保持；未作 TV 真机扫码成功的结论。

## TV 触屏唤醒标题

原 `view_widget_vod` 的 top/title/size 节点都保留在 APK。触屏唤醒的 `Y0(View)` 原分支只显示底部控制条，top 默认 gone；现在全屏播放器唤醒时同步显示同一原 top 节点，原标题和尺寸文本继续由原播放器填充。原 `o0(true)` 已会隐藏它，保留原超时/隐藏流程。

本轮没有恢复壁纸初始化、详情截图或改变视频全屏背景，保留此前已验收的黑色进场。手机顶部流程保持。

## API 地址与后续订阅约定

coos-js 公开播放器入口的 GET 根响应为 `{apiUrl: ...}`，该信息不表示它只是管理网页。对照公开路由，搜索能力位于 `api/v2/fongmi/danmaku`，读协议支持 GET。现在 coos-js 的 `/website/danmu/manage/<token>` 及标准数字 token 根地址自动补这一搜索路径，按 name/episode 提交查询；已经填写完整搜索地址或 GET 模板的地址保持。用户无需提供类型、适配字段或附加 JSON。

后续自有 TVBox 输出采用根级 `danmaku` 字符串，优先输出完整标准搜索地址。完整约定见 `docs/TVBOX-DANMAKU-CONFIG.md`。本轮不修改或发布 coos-js/V6 服务，不记录实际用户 API 凭据。

GitHub 编译 5.3.0-preview.2 / 614 四套固定签名 APK，`run_validation_tests=false`，仅保留构建所需 API23、原样/允许变化、R8 ABI 和签名步骤；正式 Latest 仍为 5.2.3。用户真机复测手动菜单、标准 API、扫码回填和 TV 触屏标题。

## 交付与只读排查

[四套固定签名测试 APK](https://github.com/leotvgo/Leotv/releases/tag/leotv-5.3.0-preview.2-build-45045541321) 已发布，源码 `a55524691b5b424535ba89be625b2ae3b4d2a517`，构建 `45045541321` 第二次尝试与发布 `45047566834` 均成功。结果保存于 `evidence/leotv-5.3.0-preview.2-delivery-20261123.json`。首次手机构建发现控制栏回调有两个返回分支，已修正挂接工具；内部映射并发空草稿冲突经核对精确 ID/源码/空资产后改名保留，重试归档完成。额外回归保持关闭。

用户随后怀疑全屏入口仍先显示原小窗，明确要求只读排查。实际路由是 DetailActivity.play → 新 Intent 直接进入带 fullscreen 标记的 VideoActivity → 原初始化 L 尾部 Playback.initialize → 同一实例的原 Y 全屏方法；没有另开小窗 Activity或模拟点击。原布局确实先被构造，但正常新建流程在 onCreate 返回/首帧布局前已调用全屏切换。原 cast 标记也是同一 Activity 内较早调用 Y，不能仅据此证明闪屏根因。现有黑色处理是窗口背景归属及跳过宿主壁纸初始化，未增加过渡动画；按用户要求不改变启动链路，继续保留。

公开订阅的只读 PNG/base64 解码得到根级 danmaku 为本机 2525 端口的 name/epid 模板，与用户 coos-js 局域网入口不同；APK 支持模板替换，实际服务可用性由订阅配套运行组件及真机决定。完整观察字段保存在交付取证，不将整个订阅配置存入仓库。
